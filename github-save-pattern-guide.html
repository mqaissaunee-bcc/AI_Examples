Saving a static web app to GitHub, with a password for each person

A single HTML file hosted on GitHub Pages can load its data from the repository, save changes back as commits, and let only people with a password make changes — no server, no database, no monthly bill. This guide walks through setting it up and explains how it works so you can reuse it in other tools.

What this does

The pattern was first built for a student project tracker, where an advisor and a student both needed to check off tasks, log test results and leave notes in one shared page. It works for any small tool where a few named people need to edit shared data:

Loads the latest version

Every time the page opens, it reads the data file straight from the repository, so everyone sees the same thing.

Saves automatically

A moment after any change, the page commits the data file back to GitHub. Each save is a commit, so the history doubles as a version log.

One password per person

Each person signs in with their own password, as an editor or a read-only viewer. The page knows who made each change and records it in the commit message.

Handles simultaneous edits

If two people save at once, the page fetches the other person’s version and reapplies its own change on top, so no edit is lost.

It is meant for small groups and modest amounts of data — a handful of people and a data file well under a megabyte. For dozens of editors or private data, use a real backend.

How it works

A static page has no server to check passwords, and anything written in its HTML can be read by anyone who views the source. So the password doesn’t unlock the page itself. It unlocks a GitHub access token — the key that allows saving — which is stored only in encrypted form.

The pieces

  • A fine-grained personal access token that can only read and write files in one repository. You create it on GitHub.
  • A one-time setup screen (open the page with ?setup on the end of the address). You paste the token and choose a password for each person. The browser encrypts the token separately with each password — PBKDF2 with 600,000 rounds to turn the password into a key, then AES-GCM encryption — and commits the result to the repo as access.json.
  • Sign-in. The page downloads access.json and tries the typed password against each encrypted copy. Whichever one opens tells the page who you are and gives it the token.
  • Saving. The page uses GitHub’s Contents API to read and commit data.json. Every write includes the file’s current version ID (its SHA); if someone else saved in the meantime, GitHub refuses the write, the page fetches the newer file, reapplies its change and tries again.

Anyone can download access.json and guess passwords against it on their own computer, as fast as their hardware allows. Use long passwords — three or four unrelated random words is plenty — and a different one for each person.

Public or private repository?

On a free GitHub account, Pages only works from a public repository. Paid plans (GitHub Pro and up) can publish from a private repository, but the published site is still public, and Pages serves every file in the published folder — including the data file. For data that isn’t sensitive, a public repository is the simplest choice.

Create the repository

Give each tool its own repository. The token will be limited to that one repository, so if a password is ever guessed, nothing else you host is at risk.

  1. On GitHub, create a new public repository, for example eva-glove-tracker. Adding a README is fine.
  2. Upload the tool’s HTML file and name it index.html. (Add file → Upload files, then commit.)
  3. Turn on Pages: Settings tab of the repository → Pages → under Build and deployment, Source: Deploy from a branch, Branch: main, folder / (root) → Save.
  4. After a minute or two, the site appears at https://<your-username>.github.io/<repository-name>/. Opening it now shows “Not set up yet” — that’s expected.

Create the fine-grained access token

Why a token at all

GitHub won’t accept a commit from a web page unless the request carries proof that someone is allowed to make it. Your GitHub password can’t be used for that, and it shouldn’t be: it opens your entire account. A personal access token is a separate, revocable key made for a single purpose. The tool sends it with each request, and GitHub treats the request as coming from you, within whatever limits the token has.

Why fine-grained instead of classic

GitHub offers two kinds of token. A classic token is broad: give it the repo scope and it can read and write every repository you have access to, including private ones and ones in organizations. A fine-grained token is built around least privilege — it gets only the specific repositories and the specific permissions you pick, and nothing more.

That matters here because the token is shared. Everyone with a tracker password unlocks the same token, and a copy of it, encrypted, sits in a public file. The question to plan around is “if this token ever leaked, what could someone do with it?” A fine-grained token keeps the answer small.

With this setup, the token canIt cannot
Read files in the one repository you chose

The other safeguards that come with it

  • Expiration. Fine-grained tokens are meant to expire. Set the date to the end of the project, and the key stops working on its own once the tool is no longer needed, even if everyone forgets about it.
  • Independent revocation. Each token can be deleted on its own. Cutting off one tool doesn’t affect any other tool or your own GitHub access.
  • A clear record. Each token is listed by name with its repository, permissions and last-used date, so it’s easy to see what exists and what it can reach.
  • Visible history. Everything the token does shows up as a normal commit in the repository, so any change, accidental or not, can be seen and undone.
Know the one remaining risk.

Within its repository, the token can change any file, not just data.json — including index.html. That’s why each tool gets its own repository: the worst case is a messed-up project page that can be restored from the commit history, not damage to your other sites. GitHub permissions can’t be narrowed to a single file, so this is as tight as it gets.

Creating it

Look in your account settings, not the repository’s.

Developer settings live under your profile picture, not the Settings tab of a repository.

  1. Click your profile picture in the top-right corner of GitHub and choose Settings.
  2. Scroll to the very bottom of the left sidebar and click Developer settings.
  3. Choose Personal access tokens → Fine-grained tokens → Generate new token. You can also go straight to github.com/settings/personal-access-tokens/new (opens in a new tab) ↗.
  4. Fill in the form as shown in the table below, then click Generate token.
  5. Copy the token right away. GitHub shows it only once. Keep it somewhere safe until setup is done; you won’t need it after that.

Run setup and set passwords

  1. Open the site with ?setup added to the end, for example https://<your-username>.github.io/eva-glove-tracker/?setup.
  2. Check the repository fields. The owner, repository and folder fill in from the address; the branch is usually main. Leave the folder blank if index.html is at the top level of the repo.
  3. Paste the token.
  4. Enter a name and password for each person. Passwords need at least 12 characters and must be different from each other.
  5. Click Save access file to GitHub. The page checks the token, encrypts it with each password, commits access.json, creates an empty data.json if there isn’t one, and signs you in.
  6. Wait a minute or two for Pages to publish access.json before signing in from another device.

Setup runs entirely in your browser. The token and passwords are sent nowhere except to GitHub — the token as the login for its API, and the passwords never at all.

Share with others

Send the plain site address — without ?setup — and each person’s password separately, for example the address by email and the password in person or by text.

When signing in, each person can tick Stay signed in on this device. That keeps the token in that browser’s storage so they skip the password next time. It should only be used on their own computer or phone, never a shared lab machine.

Add viewers and other people

Setup creates two editors. After that, the advisor account can add more people from Settings → People inside the tool, without rerunning setup. Each person gets their own password and one of two kinds of access:

AccessCanCan’t
EditorChange anything in the toolManage people (only the advisor account can)
ViewerSee every tab, present the slides, print or save them as a PDF, download a backupChange anything. Edit controls are hidden and switched off, and GitHub itself rejects any save

A viewer works well for someone who needs to follow the project without touching it, such as a grant’s project lead, a department chair or an outside mentor.

Why viewers need their own token

Hiding the edit buttons alone wouldn’t make anyone read-only: if a viewer’s password unlocked the main token, someone comfortable with browser tools could still save changes. So viewers get a second fine-grained token with Contents: Read-only. Their passwords unlock only that token, and GitHub refuses any write made with it. The read-only token is also stored once more in access.json, encrypted with the main token, so the advisor can add further viewers without pasting it again.

Create the read-only token

  1. Open Settings → Developer settings → Personal access tokens → Fine-grained tokens → Generate new token, the same place as the main token.
  2. Name it so it’s easy to tell apart, for example “EVA tracker – viewers.”
  3. Choose the same resource owner and Only select repositories → the tool’s repository.
  4. Under Repository permissions, set Contents to Read-only. Leave everything else at “No access.”
  5. Set an expiration, generate the token, and copy it.

Add a viewer

  1. Sign in to the tool with the advisor password and open Settings (top right). Scroll to People.
  2. Under Add a person, enter the person’s name, choose Viewer (read only), and set a password of 12 or more characters.
  3. For the first viewer only, paste the read-only token. Later viewers just need a name and password.
  4. Click Add person. The tool encrypts the right token with the new password and commits the updated access.json.
  5. Wait a minute or two for GitHub Pages to publish, then send the address and password separately, the same way as for editors.

Adding an editor works the same way: choose Editor, and no extra token is needed. Two people can’t share a password, because the password is what tells the tool who is signing in.

Change, reset or remove

  • Set new password next to anyone’s name gives them a new password; use it when someone forgets theirs. Change my password appears on the advisor’s own row.
  • Remove takes a person’s password off the list. The advisor account can’t remove itself.
Removing someone doesn’t sign them out everywhere.

If they chose “Stay signed in,” that browser keeps its copy of the token. For a clean cut-off, also delete and replace the token on GitHub: the read-only token for a viewer (use People → Viewer token and removing access → Replace the read-only token, then set a new password for each remaining viewer), or the main token through setup for an editor.

Renew, change, or revoke

Token expired, or you want new passwords

Create a new token (or reuse the current one if it’s still valid), open the site with ?setup again, and run setup. This replaces access.json and leaves data.json untouched. Viewers are kept, because their passwords unlock the separate read-only token. The editor list is reset to the two people entered in setup, so re-add any other editors in Settings → People. To change a single password without rerunning setup, use Set new password in People instead.

Read-only token expired

Viewers see a message that GitHub didn’t accept the access key. Create a new read-only token, replace it in Settings → People → Viewer token and removing access, then set a new password for each viewer.

Cutting off access right away

Go to Settings → Developer settings → Personal access tokens → Fine-grained tokens, open the token, and delete it. Saving stops immediately for everyone, even people who chose “Stay signed in.” Then run setup with a new token and new passwords for the people who should keep access. Deleting the read-only token cuts off every viewer the same way.

Going back to an earlier version

Every save is a commit. In the repository, open data.json, click History, and copy the contents of an older version back if needed. The tool’s Download backup button also saves a copy to your computer at any time.

Troubleshooting

“Not set up yet” right after running setup
GitHub Pages hasn’t published access.json yet. Wait a couple of minutes and reload. You can watch progress in the repository’s Actions tab.
A new viewer’s password doesn’t work yet
GitHub Pages hasn’t published the updated access.json. Wait a couple of minutes and try again.
“Paste a read-only token to add the first viewer”
The tool doesn’t have a viewer token yet, or setup was rerun with a new main token. Paste the read-only token in the Add a person form.
“That password doesn’t match”
Passwords are case-sensitive. If someone forgot theirs, rerun setup with new passwords for everyone — there is no way to recover an old one.
“GitHub didn’t accept the access key”
The token expired or was deleted. Create a new one and rerun setup.
“Repository not found, or the token doesn’t include it” during setup
The token’s Repository access doesn’t include this repository, the resource owner is wrong, or the owner/repository name has a typo.
“Not saved” with a message about GitHub refusing the save
Usually a permissions problem (the token needs Contents: Read and write) or too many requests in a short time. The page retries on its own.
“Couldn’t reach GitHub”
No internet connection. Changes stay on the page and save when the connection returns — but don’t close the tab until the status reads “Saved to GitHub.”
Lots of Pages deployments in the Actions tab
Each save is a commit, and each commit republishes the site. That’s harmless: the tool reads its data through the API, not through the published site. If GitHub ever delays a deployment, saving still works.

Reusing it in other tools

The EVA glove tracker’s index.html is the reference version; its storage, sign-in and setup code can be lifted into any tool. These are the building blocks.

The access file

What setup and the People section commit to the repository. Each person gets their own salt, nonce (iv) and encrypted token: editors’ entries hold the main token, viewers’ entries hold the read-only token. viewerKey is the read-only token encrypted with the main token, so any editor’s browser can recover it when the advisor adds another viewer.

Encrypting and decrypting the token

Built on the browser’s Web Crypto API, so no libraries are needed. It requires HTTPS, which GitHub Pages provides.

const te = new TextEncoder(), td = new TextDecoder();
const toB64 = b => btoa(String.fromCharCode(...b));
const fromB64 = s => Uint8Array.from(atob(s), c => c.charCodeAt(0));

async function deriveKey(password, salt, iterations) {
  const base = await crypto.subtle.importKey("raw", te.encode(password), "PBKDF2", false, ["deriveKey"]);
  return crypto.subtle.deriveKey(
    { name: "PBKDF2", salt, iterations, hash: "SHA-256" },
    base, { name: "AES-GCM", length: 256 }, false, ["encrypt", "decrypt"]);
}

async function encryptFor(password, token, iterations = 600000) {
  const salt = crypto.getRandomValues(new Uint8Array(16));
  const iv = crypto.getRandomValues(new Uint8Array(12));
  const key = await deriveKey(password, salt, iterations);
  const ct = await crypto.subtle.encrypt({ name: "AES-GCM", iv }, key, te.encode(token));
  return { salt: toB64(salt), iv: toB64(iv), ct: toB64(new Uint8Array(ct)) };
}

async function tryDecrypt(password, user, iterations = 600000) {
  try {
    const key = await deriveKey(password, fromB64(user.salt), iterations);
    const pt = await crypto.subtle.decrypt({ name: "AES-GCM", iv: fromB64(user.iv) }, key, fromB64(user.ct));
    return td.decode(pt);            // the token
  } catch { return null; }           // wrong password
}

Reading and committing a file

GitHub’s Contents API returns the file Base64-encoded along with its sha. Writing back requires that same sha, which is what catches simultaneous edits. The helpers below handle UTF-8 safely, so names with accents and typographic quotes survive.

const utf8ToB64 = s => { const b = te.encode(s); let bin = "";
  for (let i = 0; i < b.length; i += 0x8000) bin += String.fromCharCode(...b.subarray(i, i + 0x8000));
  return btoa(bin); };
const b64ToUtf8 = s => td.decode(fromB64(s.replace(/\s/g, "")));

function gh(cfg, path, token, opts = {}) {
  const url = `https://api.github.com/repos/${cfg.owner}/${cfg.repo}/contents/${path}`;
  return fetch(opts.method ? url : url + "?ref=" + cfg.branch, {
    method: opts.method || "GET", body: opts.body, cache: "no-store",
    headers: { "Accept": "application/vnd.github+json", "Authorization": "Bearer " + token }
  });
}

async function readFile(cfg, path, token) {
  const r = await gh(cfg, path, token);
  if (r.status === 404) return null;
  if (!r.ok) throw Object.assign(new Error("GitHub " + r.status), { status: r.status });
  const j = await r.json();
  return { sha: j.sha, text: b64ToUtf8(j.content) };
}

async function writeFile(cfg, path, text, sha, message, token) {
  const body = { message, content: utf8ToB64(text), branch: cfg.branch };
  if (sha) body.sha = sha;            // omit only when creating the file
  const r = await gh(cfg, path, token, { method: "PUT", body: JSON.stringify(body) });
  if (!r.ok) throw Object.assign(new Error("GitHub " + r.status), { status: r.status });
  return (await r.json()).content.sha;  // keep for the next write
}

Saving without losing anyone’s edits

Instead of saving the page’s current state, record each change as a small function and replay the unsaved ones on top of the latest copy from GitHub. A conflict then costs one extra read, not a lost edit.

let remote = {}, remoteSha = null, pending = [], saving = false, timer;

function change(fn) {           // call for every edit, e.g. change(s => s.tasks[id] = true)
  fn(state);                    // update the screen right away
  pending.push(fn);
  clearTimeout(timer);
  timer = setTimeout(save, 1500);   // batch quick edits into one commit
}

async function save() {
  if (saving || !pending.length) return;
  saving = true;
  const batch = pending.slice();
  try {
    for (let attempt = 0; ; attempt++) {
      const next = structuredClone(remote);
      batch.forEach(fn => fn(next));
      try {
        remoteSha = await writeFile(cfg, "data.json", JSON.stringify(next), remoteSha,
                                    "Update by " + who.name, token);
        remote = next;
        break;
      } catch (e) {
        if ((e.status === 409 || e.status === 422) && attempt < 3) {
          const f = await readFile(cfg, "data.json", token);   // someone else saved first
          remote = f ? JSON.parse(f.text) : {}; remoteSha = f ? f.sha : null;
          continue;
        }
        throw e;
      }
    }
    pending = pending.slice(batch.length);
  } finally { saving = false; if (pending.length) save(); }
}

The full version in the tracker also shows a save status, retries after network failures, warns before closing a tab with unsaved changes, and checks for other people’s changes every 45 seconds.

Adapting the tracker for a new tool

  • Replace the tracker’s content (phases, materials, views) with the new tool’s, and keep the storage, sign-in and setup sections as they are.
  • Route every edit through mutate(fn) so it is saved and replayable.
  • Change the defaults() function to describe the new tool’s empty data.
  • Keep the role names: advisor manages people, student or editor can change everything, and viewer is read-only. Hiding things for editors is a convenience, not security, since all editors share one token; the viewer role is enforced by GitHub through the read-only token.
